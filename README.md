# 음악학원·음악학교 운영 플랫폼

**동시 요청이 몰려도 예약이 겹치지 않는 학원·연습실 운영 서비스.** 여러 학원과 학교가 각자 공간을 만들고, 연습실 예약이나 원생·수강 관리를 골라 쓴다.

> 전신(v1)은 단국대학교 뉴뮤직학부 연습실 예약 서비스다. 2025-03부터 2026-07까지 학생들이 실제로 썼다(FastAPI, [`legacy-fastapi`](../../tree/legacy-fastapi) 브랜치). v2는 그때 배운 규칙을 요구사항으로 옮겨 Spring으로 새로 만든 것이다. **지금은 실사용자가 없다.** 그래서 부하와 경쟁 상황을 일부러 만들어 검증했다.
>
> 상태: MVP 기능 구현 완료(계정·기관·멤버, 연습실, 학원 관리). 배포와 2차 기능(알림, 결제)은 진행 중이다.

## 구성
```
브라우저 (React + Vite, 휴대폰 우선)
   │
Spring Boot 4.1 (Java 25, 모듈러 모놀리스: 기관 · 연습실 · 학원 관리)
   │
PostgreSQL 17 (EXCLUDE 제약, advisory lock, 연락처 AES-GCM)
```
- 한 서비스에 여러 기관이 있다(멀티테넌시). 모든 기관 범위 요청은 인터셉터 한 곳에서 "활성 멤버인가 → 모듈이 켜져 있나 → 역할" 순서로 검사하고, 권한 표시가 없는 API는 기본으로 거부한다.
- 기관마다 모듈(연습실, 학원 관리)을 켜고 끈다. 모듈 사이 의존 방향은 ArchUnit 테스트로 검사한다.

## 대표 문제 1. 같은 시간에 몰린 예약이 겹치지 않게

**문제**
- 매주 정해진 시각(v1은 금요일 09:00)에 예약이 열리면 요청이 한꺼번에 몰린다.
- 지켜야 할 규칙은 셋이다: 같은 방(R1), 같은 사람(R2, 방이 달라도), 하루 이용 한도(R4).

**원인**
- "겹치는 예약이 있나 조회 → 없으면 저장"은 두 요청이 동시에 조회를 통과하면 둘 다 저장된다.
- 기존 행에 `SELECT … FOR UPDATE`를 걸어도, 아직 겹치는 행이 없으면 잠글 대상이 없다(phantom). 흔한 "재고 1 감소" 예제와 달리 이것은 **구간이 겹치면 안 된다는 범위 규칙**이다.
- 하루 한도는 합계 규칙이라, 서로 겹치지 않는 두 예약이 각자 검사를 통과하는 write skew가 생긴다.

**해결: 4가지 방식을 같은 조건에서 쟀다** ([실험 0001](docs/experiments/0001-예약-겹침-방지-비교.md), 같은 방에 1,000건 동시, 3회)

| 방식 | 저장된 행 (정답 1) | 처리량 (req/s) | p99 | 비고 |
|---|---|---|---|---|
| 아무 조치 없음 | 20 | 9,308~10,082 | 0.1초 | 문제 재현 |
| 겹치는 행 `FOR UPDATE` | 20 | 2,164~2,416 | 0.4~0.5초 | phantom이라 못 막음 |
| advisory lock (방·날짜) | **1** | 1,149~1,257 | **0.8~0.9초** | 오류 0 |
| `EXCLUDE` 제약만 | 1 | 2 | 474~498초 | 정확하지만 1,000건 중 569~594건이 교착 |

- `EXCLUDE` 제약만 두면 데이터는 정확하지만, 한 칸에 몰리면 대기 중인 트랜잭션끼리 교착이 나서 절반 넘는 요청이 오류와 몇 분의 대기를 받는다. PostgreSQL 소스 주석이 설명하는 동작이다(배타 제약은 인덱스 항목을 먼저 넣고 충돌을 나중에 검사한다).
- **대가:** 요청이 50개 방에 흩어지면 `EXCLUDE`만으로도 정확하고, 처리량은 `EXCLUDE`만 약 10,000 req/s, advisory lock 약 7,000 req/s로 잠금 쪽이 약 30% 느리다. 이 서비스의 실제 부하는 예약 오픈 순간 한 칸에 몰리는 쪽이라, 흩어진 부하의 30%를 내주고 몰림에서의 교착과 수백 초 대기를 없애는 쪽을 골랐다.

**결론 ([ADR 0010](docs/adr/0010-예약-겹침-방지.md))**
- 방·날짜 advisory lock으로 같은 방 요청을 줄 세운다.
- 이어서 사람·날짜 잠금 안에서 R2와 R4를 검사한다. 예약이 자정을 넘지 않으므로 같은 사람의 겹침과 합계는 같은 날 안에서 끝난다.
- 잠금 순서는 방 → 사람으로 고정하고, `EXCLUDE USING gist` 배타 제약은 마지막 방어선으로 둔다.
- 정책 검사(시간 단위, 운영 시간, 최대 연속, 예약 오픈)는 잠금 밖에서 먼저 해서 트랜잭션을 짧게 둔다. 시각은 `Clock`을 주입한 순수 함수라 경계(금 08:59와 09:00 등)를 단위 테스트로 고정했다.

**결과**
- 같은 방 1,000건 동시: 저장 1건, 오류 0, p99 약 0.8초
- 하루 한도 동시성 테스트: 사람·날짜 잠금을 빼면 3회 모두 한도를 넘어 저장되고, 넣으면 통과한다.
- 실제 브라우저 두 개로 같은 칸을 동시에 잡으면 늦은 쪽은 "방금 다른 사람이 예약했어요"를 보고 시간표가 새로 고쳐진다.

## 대표 문제 2·3 (2차 진행 중)
- **메시지 전달 보장:** 휴강·결제 안내를 발송사 장애를 일부러 일으켜도 누락 0건, 중복 0건으로 보낸다(Transactional Outbox).
- **결제 정합성:** PG 웹훅이 중복되거나 순서가 바뀌어도 이중 결제 0건, 일일 대사로 불일치를 검출한다.

## 그 밖에 동시성으로 지키는 것
| 상황 | 막는 방법 | 검증 |
|---|---|---|
| 소유자 둘이 서로를 동시에 강등 (소유자 0명) | 기관 행 잠금 후 남은 소유자 수 확인 | 잠금을 빼면 실패하는 테스트 |
| 같은 초대 링크를 동시에 수락 | 조건부 UPDATE (`used_at IS NULL`) | 6명 동시 수락 중 1명만 성공 |
| 학생과 관리자가 같은 예약을 동시에 취소 | 조건부 UPDATE | 동시 5회 |
| 관리자가 낡은 화면에서 수강을 또 연장 (이중 연장) | 화면이 가진 version을 요청에 실어 비교 | 실제 두 창으로 409 확인 |
| 같은 이메일로 동시 가입 | 유니크 인덱스 | 동시 8건 중 1건 |

## 어떻게 검증했나
- **통합 테스트 90개:** Testcontainers로 실제 PostgreSQL에서 돈다. 기관 범위 API에는 "다른 기관으로 접근하면 막힌다" 테스트가 있다. CI(GitHub Actions)에서 모든 push마다 돈다.
- **실제 연결 확인:** 기능마다 백엔드와 프론트를 띄우고 브라우저로 여러 계정(원장, 강사, 학생)을 동시에 움직여 끝까지 눌러 봤다(360px 휴대폰 화면 포함).
- **교차 리뷰:** 설계는 두 작업자가 따로 쓴 뒤 서로 반박해 합쳤고, 구현은 서로의 코드를 리뷰했다. 그렇게 잡은 문제 중 일부:

| 어디서 | 문제 | 고친 방법 |
|---|---|---|
| 스키마 | `CHECK`의 OR 분기에서 비교 대상이 NULL이면 결과가 NULL이라 통과 | OR 분기에 `IS NOT NULL` 명시 |
| 가입 | 한글 비밀번호 30자(90바이트)가 BCrypt 72바이트 한도에 걸려 500 | 바이트 길이 검증 |
| 인증 | 만료된 토큰이 붙은 로그인 요청이 401 | 인증 경로에서는 Bearer를 읽지 않음 |
| 기관 검사 | 기관 ID "06"으로 모듈 검사를 건너뜀 | 매칭된 경로 패턴으로 판단, 다른 표기는 404 |
| 소셜 로그인 설계 | 남의 이메일로 먼저 가입해 두면 진짜 주인의 구글 로그인이 그 계정에 연결됨 (사전 계정 탈취) | 기존 계정과 자동 연결하지 않음 |
| 구글 로그인 | 트랜잭션 안에서 외부 HTTP를 불러 구글이 느리면 DB 커넥션을 쥔 채 대기 | 검증을 트랜잭션 밖으로, 타임아웃 5초 |
| 예약 화면 | 날짜를 빨리 바꾸면 늦게 온 이전 응답이 새 결과를 덮어씀 | 지난 요청의 응답은 버림 |
| 예약 | 겹친 예약의 시각이 UTC로 나가 10:00 예약이 "01:00"으로 보임 | 모든 응답 시각을 기관 시간대로 |
| 수강 | 낡은 화면에서 한 번 더 연장 가능 | 화면이 읽은 version을 비교 |

> **AI 도구:** 이 프로젝트는 AI 코딩 도구(Claude Code)로 작성했다. "두 작업자"는 같은 저장소에서 따로 일한 AI 세션 둘이고, 범위와 결정은 작성자가 정했다. 결과는 테스트, 실험, 실제 브라우저 연결로 검증했다.

## v1 → v2에서 바뀐 것
| v1에서 배운 것 | v2 |
|---|---|
| 동시 요청에 앱 검사만으로는 겹친 예약이 들어갈 수 있었음 (advisory lock으로 해결) | DB 제약까지 내려서 지키고, 방식은 실험으로 고름 |
| 평면도와 정책이 코드에 있으면 바꿀 때마다 재배포 | 관리자가 격자 위에 직접 그리고 정책을 바꿈 |
| 한 학부 전용 | 누구나 기관을 만들고 모듈을 골라 씀 |
| 비밀번호 평문 저장을 운영 중에 발견 | 처음부터 해시, 연락처는 AES-GCM 암호화 + 화면 마스킹 |

## 측정 환경
Apple M1 Max(10코어) 노트북 한 대에서 부하 발생기(JVM)와 PostgreSQL 17(Docker, CPU 10개, 메모리 7GiB)이 함께 돈다. 커넥션 풀은 HikariCP 20개, `deadlock_timeout`은 기본값 1초다. 네트워크 지연이 거의 없는 조건이라 절대값보다 **방식 사이의 차이**를 봐 주면 좋겠다.

## 실행
필요한 것: Java 25, Node 24, Docker
```bash
docker compose up -d                          # PostgreSQL 17 (개발용)
cd backend && ./gradlew bootRun               # :8080 (로컬 키는 자동 설정)
cd frontend && npm install && npm run dev     # :5173, /api는 8080으로 프록시
cd backend && ./gradlew test                  # Testcontainers가 DB를 따로 띄움
cd backend && ./gradlew experiment            # 실험 0001을 다시 돌려 문서를 새로 씀 (약 25분)
```
