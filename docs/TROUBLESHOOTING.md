# 트러블슈팅 기록

연습실 예약 시스템과 아티스트 포트폴리오 플랫폼(SEIHI) 작업 중 실제로 겪은
문제를 증상부터 기록한다. 헛짚었던 것도 그대로 남긴다 — 처음 짚은 원인이
맞았던 적이 별로 없었다.

---

## 1. 동시에 같은 시간대를 요청하면 여러 건이 들어갈 수 있다

**증상**
예약 생성 코드가 "겹치는 예약이 있는지 SELECT로 확인 → 없으면 INSERT"
순서로만 짜여 있었다. README에도 이 위험을 스스로 적어 뒀다: "두 요청이
정확히 같은 순간에 같은 시간대를 요청하면, 둘 다 충돌 검사를 통과한 뒤 둘 다
삽입될 수 있다." 예약이 매주 금요일 09:00에 한꺼번에 열리는 구조라 요청이
몰리는 순간이 실제로 있다.

**처음 의심**
`UNIQUE(room_id, start_date, start_time)` 하나면 될 줄 알았다. 두 번째
INSERT가 그 자리에서 막히니 단순하고 확실해 보였다.

**어떻게 좁혔나**
예약 길이가 1~2시간 가변이라는 걸 다시 봤다. `09:00-11:00`이 이미 있는 방에
`10:00-12:00`이 들어오면 실제로는 겹치는데 `start_time`이 09:00과 10:00으로
달라서 유니크 제약에 걸리지 않는다 — 겹침은 구간 비교로만 판정되는데
유니크 제약은 정확히 같은 값만 잡는다. 다음으로 `SELECT ... FOR UPDATE`를
검토했는데, 이건 **존재하는 행만** 잠근다. 그 시간대에 예약이 하나도 없는
상태(오픈 직후가 정확히 이 상태)에는 잠글 행 자체가 없어 두 트랜잭션이 동시에
"충돌 없음"을 보고 통과할 수 있다.

**원인**
행이 아니라 "이 방·이 날짜"라는 키를 직접 잠가야 하는 문제였다. 행의 존재
여부와 무관하게 같은 키를 요청하는 트랜잭션을 직렬화해야 한다.

**조치**
`pg_advisory_xact_lock`으로 방·날짜를 잠근다. 방(`room_id`)은 음수로,
사용자(`user_id`)는 양수로 걸어 두 키 공간이 겹치지 않게 했고,
`date.toordinal()`로 날짜를 정수로 바꿨다(해시가 아니라 전단사라 충돌 여지가
없다). 락은 항상 방 → 사용자 순서로 고정해 데드락 사이클을 없앴다.

세션 레벨(`pg_advisory_lock`)이 아니라 트랜잭션 레벨을 쓴 이유가 따로 있다.
DB 연결 문자열이 Neon의 PgBouncer transaction-mode 풀러였다 — 이 모드에서는
트랜잭션이 끝날 때마다 물리 커넥션이 바뀔 수 있어서, "잠근 커넥션 = 나중에
푸는 커넥션"을 전제하는 세션 레벨 락은 다른 요청의 커넥션에 묶이거나 영영
안 풀릴 수 있다. 트랜잭션 레벨은 COMMIT/ROLLBACK에서 자동 해제되므로 이
문제가 없다.

**확인**
같은 방·같은 날짜·겹치는 시간대에 8명이 동시에 요청했을 때 1건만 성공했고
DB에도 1행만 남았다.

## 2. 재예약이 시간대와 무관하게 전부 막힌다

**증상**
같은 사용자가 그날 이미 예약이 있는 상태에서 다른 방·다른(겹치지 않는)
시간대를 예약하려 하면 매번 "같은 날짜에 이미 예약이 있어 이전 예약의 종료
시각 이후에만 재예약할 수 있습니다"로 거절됐다. 재현하면:

```
① room1 09:00-10:00  → 201
② room2 09:30-10:30  → 400 "이전 예약 종료 이후에만"   (겹침, ②가 막음)
③ room2 10:00-11:00  → 201                              (안 겹침, 통과)
④ room3 08:00-09:00  → 400 "이전 예약 종료 이후에만"   (안 겹치는데 막힘)
```

④가 문제였다 — room3 08:00-09:00은 기존 예약(room1 09:00-10:00, room2
10:00-11:00) 어느 것과도 시간이 겹치지 않는데도 막혔다.

**처음 의심**
"같은 방·다른 사용자 충돌"(방 충돌 검사)과 헷갈린 버그인 줄 알았다.

**어떻게 좁혔나**
코드를 보니 재예약 검사(②)가 `now`(현재 벽시계 시각)를 이전 예약의 종료
시각과 비교하고 있었다. 바로 위에서 신규 예약의 시작 시각(`dt_start`)을 이미
계산해 두고도 쓰지 않은 상태였다. 예약은 항상 미래 날짜라 `now`는 그 예약이
실제로 시작하기 전까지 이전 예약 종료 시각보다 거의 항상 작다 — 그래서
시간대와 무관하게 매번 막힌 것이었다.

**원인**
비교 대상이 "신규 예약의 시작 시각"이어야 하는데 "현재 시각"으로 돼 있었다.
`now` ↔ `dt_start` 한 글자 차이가 아니라 아예 다른 값이었다. 이 버그의 더
중요한 파생 효과는 따로 있었다: "같은 사람이 같은 시간에 다른 방을 잡는 것"을
막는 검사(④, 방 충돌과 별개로 있는 검사)가 이 재예약 검사보다 뒤에 있어서,
재예약 검사가 매번 먼저 막아 버리는 바람에 **④ 검사 자체가 한 번도 실행될
기회가 없었다.** README는 ④를 "실제 운영 문제 해결책"이라고 설명하고
있었는데, 그 코드가 살아있는 적이 없었던 셈이다.

**조치**
비교를 `now` 대신 `dt_start`로 바꿨다. 정책(`same_day_mode`)으로 세 가지
모드를 두어 "겹치지만 않으면 순서 무관"(기본값)을 포함해 운영진이 규칙
자체를 고를 수 있게 했다.

**확인**
같은 4단계를 다시 실행해 room3 08:00-09:00이 201로 성공하는 것을 확인했다.
기본 모드에서는 room2 09:30-10:30처럼 실제로 겹치는 요청만 거절되고,
겹치지 않는 요청은 시간 순서와 무관하게 통과한다.

## 3. 평면도가 화면에 안 보인다

**증상**
평면도 격자에서 복도·벽에 해당하는 칸을 색으로 채워야 하는데, CSS 값을
분명히 올렸는데도 화면에서는 배경색과 거의 구분이 안 됐다.

**처음 의심**
색 자체를 잘못 골랐다고 생각했다 — 옅은 회색(`--c-surface-2`)이 배경과 너무
가까워서라고 보고 진한 회색(`--c-border`)으로 바꿨다. 그런데도 그대로였다.

**어떻게 좁혔나**
CSS 로드 순서를 다시 봤다. `common.css → admin.css → user.css` 순으로
로드되는데, 같은 선택자(`.cell.filled`)를 `admin.css`가 나중에(user.css보다
먼저지만 관리자 화면 스타일 정리 과정에서) `opacity: 0.35`로 다시 정의하고
있었다. 색상값 자체는 `user.css`가 이겼지만 `opacity`는 `admin.css`
쪽이 이기고 있었다 — 진한 색을 칠해도 35% 불투명도로 다시 흐려지고
있었던 것이다.

**원인**
색상과 불투명도가 서로 다른 파일에, 서로 다른 명시도로 나뉘어 있었다.
색만 보고 고치면 안 보이는 종류의 충돌이었다.

**조치**
`.cell.filled`의 명시도를 올려(`#grid .cell.filled, .cell.filled`) `opacity: 1`을
명시적으로 다시 선언했다.

**확인**
평면도를 다시 열어 ㄱ자로 꺾인 복도 모양이 실제로 눈에 보이는 것으로
확인했다. 스크린샷 비교 없이 색상 코드값만 봐서는 이 문제를 못 잡았을
것이다 — 렌더된 화면을 직접 봐야 했다.

## 4. 테스트가 운영 DB에 붙을 뻔했다

**증상**
pytest 스위트를 새로 짜면서 `DATABASE_URL`을 스크래치 Postgres로 미리
`os.environ`에 심어 뒀다. 그런데 `backend/.env`가 실제로 존재했고 운영
Neon 자격증명이 들어 있었다.

**처음 의심**
환경변수를 먼저 설정해 뒀으니 당연히 그 값이 쓰일 거라 생각했다.

**어떻게 좁혔나**
`app/database.py`를 다시 읽었다. 모듈이 임포트되는 순간 이렇게 동작하고
있었다:

```python
dotenv_path = find_dotenv()
if dotenv_path:
    load_dotenv(dotenv_path, override=True)
```

`override=True`가 핵심이었다 — `.env` 파일에 있는 값이 이미 설정된
환경변수를 덮어쓴다. `find_dotenv()`는 현재 작업 디렉터리부터 위로 올라가며
`.env`를 찾으므로, pytest를 `backend/` 밑 어디서 실행하든 `backend/.env`를
찾아낸다. 즉 테스트 코드가 아무리 먼저 스크래치 DB 주소를 심어 놔도, 앱
코드를 임포트하는 순간 운영 값으로 덮어써졌다.

**원인**
"먼저 설정하면 이긴다"는 가정이 틀렸다 — `override=True`가 있으면 나중에
로드되는 `.env`가 항상 이긴다.

**조치**
`conftest.py` 맨 위, `app.*`를 임포트하기 전에 `dotenv.find_dotenv`/
`load_dotenv`를 아무 일도 하지 않는 함수로 바꿔치기했다. 여기서 멈추지 않고
`database.py` 자체도 `load_dotenv(..., override=False)` + `find_dotenv(usecwd=True)`로
고쳐, 바깥에서 준 환경변수가 항상 `.env`를 이기도록 근본에서 바꿨다 —
방어를 테스트 코드 한 곳에만 두면 다음에 또 같은 함정에 걸릴 수 있다.
같은 패턴(`override=True` 기반 `.env` 로딩)이 SEIHI 저장소의 Alembic
`env.py`에도 있었고, 거기서는 실제로 읽기 전용 명령 한 번이 운영 Neon에
그대로 연결됐다 — 한 저장소에서 잡은 문제가 다른 저장소에도 있었다.

**확인**
```
환경변수 지정 시  → localhost:5433 (스크래치)
환경변수 없을 때  → ...neon.tech
```
수정 전에는 두 경우 모두 운영 주소로 귀결됐고, 수정 후에는 지정한 값이
그대로 유지되는 것을 직접 확인했다.

## 5. 모바일 화면을 고쳐도 스크린샷은 계속 깨져 보인다

**증상**
SEIHI 프론트엔드 모바일 점검 중, 가로 스크롤 원인을 찾아 고쳤는데도 검증용
스크린샷(`--headless=new --window-size=390,1200 --screenshot=...`)을 다시
찍으면 여전히 히어로 제목과 "DISCOVER NEW SOUNDS"가 잘려 있었다.

**처음 의심**
고친 CSS가 실제로 반영이 안 됐다고 생각했다 — 캐시나 HMR 문제를 의심했다.

**어떻게 좁혔나**
캐시를 의심하기 전에 먼저 도구 자체를 의심해야 한다는 걸 뒤늦게 깨달았다.
Chrome DevTools Protocol로 직접 붙어 같은 페이지의 `window.innerWidth`를
확인했다: `--window-size=390,1200`을 준 상태인데도 **500**이 나왔다. 파일로
저장된 스크린샷은 정확히 390×1200 픽셀이었지만, 그 안에 그려진 페이지
자체는 390px 뷰포트로 레이아웃되지 않고 있었다 — 더 넓게 렌더된 걸 390px
이미지로 잘라내거나 축소한 것이었다.

**원인**
`--window-size`는 창 크기를 지정할 뿐, `<meta name="viewport">`가 기대하는
모바일 레이아웃 뷰포트를 보장하지 않는다. CDP `Emulation.setDeviceMetricsOverride`에
`mobile: true`를 명시적으로 줘야 실제로 390px 기준 미디어쿼리(`max-md:`
등)가 걸린 레이아웃이 나온다.

**조치**
검증 스크립트를 `Emulation.setDeviceMetricsOverride({width, height,
deviceScaleFactor: 1, mobile: true})` 기반으로 바꿨다.

**확인**
같은 코드를 두 가지 방법으로 동시에 찍어 비교했다. `--window-size`만 쓴
스크린샷은 CSS 수정 이후에도 여전히 텍스트가 잘려 있었고(거짓 실패), CDP
`mobile:true` 방식으로 찍은 스크린샷은 `document.documentElement.scrollWidth`가
`window.innerWidth`와 정확히 390으로 일치했고 텍스트도 잘리지 않았다. 이후
모바일 스크린샷은 전부 이 방식으로 다시 찍었다 — 기존에 "여전히 깨져 있다"고
판단했던 것 중 일부가 실제로는 이미 고쳐진 상태를 도구가 잘못 찍은
것이었다.

## 6. 겹침 원인이 증상이 나타난 자리에 없었다

**증상**
SEIHI 홈 화면을 390px 폭에서 열면 히어로 제목("가치를 위한, 기록의 첫
걸음")과 그 아래 "DISCOVER NEW SOUNDS" 문구가 오른쪽에서 잘려 보이고
페이지 전체에 가로 스크롤이 생겼다.

**처음 의심**
제보된 목록에 있던 고정 픽셀 폭 클래스들(`w-[1280px]`, `w-[737px]` 등)이
원인일 거라 보고 그 컴포넌트들부터 확인했다. 그런데 열어보니 대부분 이미
`max-md:w-full` 같은 반응형 짝이 붙어 있었다 — 그 목록은 원인이 아니었다.

**어떻게 좁혔나**
CDP로 390px 뷰포트를 정확히 맞춘 뒤(5번에서 확립한 방법) 페이지의 모든
요소를 순회하며 `getBoundingClientRect()`가 뷰포트 폭을 넘는 요소를
찾았다. `document.documentElement.scrollWidth`가 390보다 크게 나왔고,
넘치는 요소를 좁혀 보니 "DISCOVER NEW SOUNDS" 한 줄을 감싼
`display:"inline-flex"` 컨테이너였다.

**원인**
그 컨테이너에 `flex-wrap` 지정이 없어(기본값 `nowrap`) 좁은 화면에서도
한 줄로 유지되고 있었다. 이 요소 하나가 실제 폭보다 넓어지면서 페이지
전체의 최소 폭을 그만큼 밀어 올렸고, 히어로 섹션을 포함해 페이지의 다른
모든 요소가 그 넓어진 문서 기준으로 다시 배치됐다 — 히어로 제목 자체는
잘못된 데가 없었는데도, 문서 전체가 넓어진 여파로 오른쪽이 잘려 보인
것이다. 증상이 보인 자리(히어로)와 원인이 있는 자리(그 아래 섹션의 한
줄)가 서로 달랐다.

**조치**
그 컨테이너에 모바일 폭에서만 `flex-wrap: wrap` + `justify-content: center`를
추가했다. 데스크톱 레이아웃은 그대로 두기 위해 이 규칙은 좁은 화면
전용으로 넣었다.

**확인**
