# 0002. v1을 고치지 않고 새로 만든다

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-10-06 |

## 맥락
v1은 한 학부 전용 연습실 예약 서비스였다 (FastAPI, PostgreSQL, 2025-03~, 실험 단계까지 운영). v2는 여러 기관이 각자 공간을 만들고, 모듈을 골라 쓰고, 학원 관리까지 하는 플랫폼이다.

v1 구조에서 바뀌어야 하는 것:
- 모든 테이블에 기관 구분이 없다. 사용자 역할도 서비스 전체에 하나뿐이다 (`pending` / `user` / `admin`).
- 예약 정책과 평면도가 서비스에 하나씩만 있다.
- 학원 관리 영역(원생, 수강, 레슨 기록)이 없다.

## 결정
v1 코드를 옮기지 않고 새로 만든다. 코드는 `legacy-fastapi` 브랜치와 `v1-fastapi` 태그에 보관한다. **v1에서 운영하며 배운 규칙과 문제는 요구사항으로 옮긴다** ([요구사항 정의서](../requirements/01-요구사항-정의.md) 1절).

## 검토한 대안
| 대안 | 장점 | 버린 이유 |
|---|---|---|
| v1에 기관 개념을 덧붙이기 | 이미 동작하는 코드를 쓴다 | 거의 모든 테이블, 쿼리, 권한 검사를 바꿔야 한다. 고치는 양이 새로 만드는 양과 비슷하다 |
| v1을 FastAPI 그대로 두고 새 기능만 추가 | 언어를 바꾸는 비용이 없다 | 아래 0003의 이유로 언어도 바꾼다 |

## 결과
- 기관, 모듈, 역할을 처음부터 전제로 설계한다.
- v1에서 검증한 것(겹침 판정, advisory lock, 정책을 데이터로 두기)을 다시 구현해야 한다. 대신 v2에서는 DB 제약까지 내려서 더 강하게 지킨다.
- v1의 데이터는 옮기지 않는다. v1은 실험 단계까지 운영했고 옮길 실사용자가 없다.
