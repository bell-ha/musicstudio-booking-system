# 0010. 예약 겹침은 DB 배타 제약을 마지막 방어선으로 막는다

| 상태 | 날짜 |
|---|---|
| 채택 (실험 0001로 확정) | 2026-10-06 |

## 맥락
연습실 예약 규칙 중 동시 요청에서도 지켜져야 하는 것이 세 가지다 ([유스케이스](../requirements/02-유스케이스.md) UC-23).
- R1: 같은 방의 예약끼리 겹치지 않는다
- R2: 같은 사람의 예약끼리 겹치지 않는다 (방이 달라도)
- R4: 같은 날 한 사람의 이용 합계가 정책 한도 이하다

"조회해서 겹치는 게 없으면 저장"하는 방식은 두 요청이 동시에 조회를 통과하면 둘 다 저장된다. 겹치는 기존 행에 `SELECT ... FOR UPDATE`를 걸어도, 아직 겹치는 행이 없을 때는 잠글 대상이 없어서 막지 못한다 (phantom). v1은 방·날짜와 사용자·날짜를 키로 하는 트랜잭션 단위 advisory lock으로 풀었고, 8명 동시 요청에서 1건만 성공하는 것을 확인했다.

R4는 겹침이 아니라 합계 규칙이다. 겹치지 않는 두 예약이 각자 한도 검사를 통과한 뒤 둘 다 저장되면 합계가 한도를 넘는다 (write skew). 배타 제약으로는 막을 수 없다.

## 결정
- **R1(같은 방):** 방·날짜 키 트랜잭션 단위 advisory lock으로 같은 방 요청을 줄 세운다.
- **R2(같은 사람), R4(하루 한도):** 이어서 사람·날짜 키 advisory lock을 잡고 그 안에서 검사한다. 예약은 자정을 넘지 않으므로 같은 사람의 겹침과 합계는 같은 날 안에서 끝난다.
- **잠금 순서는 방 → 사람으로 고정한다.** 잠금을 거는 다른 경로도 이 순서를 따른다.
- **`EXCLUDE USING gist` 배타 제약 2개(방, 사람)는 마지막 방어선으로 둔다.** 잠금을 빠뜨린 경로가 생겨도 겹친 예약은 저장되지 않는다.
- 교착·잠금 실패가 생기면 500이 아니라 409 `TRY_AGAIN`으로 응답한다.

## 근거: 실험 0001
[docs/experiments/0001](../experiments/0001-예약-겹침-방지-비교.md). 같은 방에 1,000건 동시, 3회. M1 Max 노트북 한 대, PostgreSQL 17, 커넥션 풀 20.

| 방식 | 저장된 행 (정답 1) | 처리량 (req/s) | p99 | 비고 |
|---|---|---|---|---|
| 아무 조치 없음 | 20 | 9,308~10,082 | 0.1초 | 문제 재현 |
| 겹치는 행 `FOR UPDATE` | 20 | 2,164~2,416 | 0.4~0.5초 | phantom이라 못 막음 |
| advisory lock (방·날짜) | **1** | 1,149~1,257 | **0.8~0.9초** | 오류 0 |
| `EXCLUDE` 제약만 | 1 | **2** | **474~498초** | 교착 569~594건 |

- 요청이 50개 방에 흩어지면 `EXCLUDE`만으로도 정확하고 빠르다(약 10,000 req/s). advisory lock은 약 30% 느리다(약 7,000 req/s). 이 서비스의 실제 부하는 예약 오픈 순간 한 칸에 몰리는 쪽이라 잠금을 고른다.
- `EXCLUDE`만으로 교착이 나는 이유는 PostgreSQL 소스 주석에 있다: 배타 제약은 인덱스 항목을 먼저 넣고 충돌을 나중에 검사하므로, 동시에 넣은 두 트랜잭션이 서로를 기다릴 수 있고 교착 감지기가 하나를 끊는다 ([execIndexing.c](https://github.com/postgres/postgres/blob/master/src/backend/executor/execIndexing.c)).

## 실험 계획
같은 방, 같은 시간에 1,000건을 동시에 보낸다. 측정 환경(사양, 커넥션 풀 크기, 데이터 양)을 함께 기록한다.

| # | 방식 | 예상 |
|---|---|---|
| 0 | 아무 조치 없음 | 여러 건 성공. 문제 재현 |
| 1 | 겹치는 기존 행에 `FOR UPDATE` | 실패. 잠글 행이 없다 (phantom) |
| 2 | advisory lock (방·날짜 키, 트랜잭션 단위). v1 방식 | 성공. 날짜가 다르면 서로 막지 않는다 |
| 3 | `EXCLUDE` 제약만 | 성공. 충돌이 제약 위반 예외로 온다 |

시간이 남으면 부모 행 `FOR UPDATE`, 낙관적 잠금, `SERIALIZABLE`을 더한다. 처음부터 다 하지 않는다.

- 지표: 성공 건수, 처리량, p50·p99, 재시도·직렬화 실패·교착 수
- 다른 시간대 예약이 섞인 부하에서도 따로 잰다
- 예약 오픈 순간의 몰림(NFR-02)을 k6로 재현한다

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 애플리케이션 검사만 | 동시 요청에서 깨진다 (v1에서 확인) |
| advisory lock만 (v1 방식) | 잠금을 빠뜨린 코드 경로가 생기면 DB가 막아 주지 못한다 |
| 유니크 제약 `(방, 날짜, 시작 시각)` | 예약 길이가 달라서 09:00~11:00과 10:00~12:00처럼 시작이 다르면서 겹치는 경우를 못 막는다 (v1에서 확인) |
| Redis 분산 잠금 | DB 안에서 풀 수 있는 문제에 저장소를 하나 더 늘린다. 잠금이 커밋보다 먼저 풀리는 문제도 생긴다 |

## 결과
- 같은 방이 몰릴 때 정확하고 오류 없이 처리한다. 흩어진 부하에서는 잠금 왕복만큼 느려진다.
- 하루 한도 동시성 테스트: 사람·날짜 잠금을 빼면 3회 모두 한도를 넘어 저장되고, 넣으면 통과한다.
- 실험은 `cd backend && ./gradlew experiment`로 다시 돌릴 수 있다.
