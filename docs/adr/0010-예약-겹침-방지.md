# 0010. 예약 겹침은 DB 배타 제약을 마지막 방어선으로 막는다

| 상태 | 날짜 |
|---|---|
| 제안 (실험 후 확정) | 2026-10-06 |

## 맥락
연습실 예약 규칙 중 동시 요청에서도 지켜져야 하는 것이 세 가지다 ([유스케이스](../requirements/02-유스케이스.md) UC-23).
- R1: 같은 방의 예약끼리 겹치지 않는다
- R2: 같은 사람의 예약끼리 겹치지 않는다 (방이 달라도)
- R4: 같은 날 한 사람의 이용 합계가 정책 한도 이하다

"조회해서 겹치는 게 없으면 저장"하는 방식은 두 요청이 동시에 조회를 통과하면 둘 다 저장된다. 겹치는 기존 행에 `SELECT ... FOR UPDATE`를 걸어도, 아직 겹치는 행이 없을 때는 잠글 대상이 없어서 막지 못한다 (phantom). v1은 방·날짜와 사용자·날짜를 키로 하는 트랜잭션 단위 advisory lock으로 풀었고, 8명 동시 요청에서 1건만 성공하는 것을 확인했다.

R4는 겹침이 아니라 합계 규칙이다. 겹치지 않는 두 예약이 각자 한도 검사를 통과한 뒤 둘 다 저장되면 합계가 한도를 넘는다 (write skew). 배타 제약으로는 막을 수 없다.

## 결정 (제안)
- **R1, R2:** `EXCLUDE USING gist` 배타 제약을 DB의 마지막 방어선으로 둔다. 애플리케이션에 버그가 있어도 겹친 예약은 저장되지 않는다.
- **그 위에** 애플리케이션 쪽 직렬화 방식을 하나 둔다. 후보는 아래 실험으로 고른다.
- **R4:** 사용자·날짜 단위로 직렬화한다 (advisory lock 또는 SERIALIZABLE). 실험으로 고른다.

## 실험 계획
같은 방, 같은 시간에 1,000건을 동시에 보낸다. 측정 환경(사양, 커넥션 풀 크기, 데이터 양)을 함께 기록한다.

| # | 방식 | 예상 |
|---|---|---|
| 0 | 아무 조치 없음 | 여러 건 성공. 문제 재현 |
| 1 | 겹치는 기존 행에 `FOR UPDATE` | 실패. 잠글 행이 없다 (phantom) |
| 2 | advisory lock (방·날짜 키, 트랜잭션 단위). v1 방식 | 성공. 날짜가 다르면 서로 막지 않는다 |
| 3 | `EXCLUDE` 제약만 | 성공. 충돌이 제약 위반 예외로 온다 |

시간이 남으면 부모 행 `FOR UPDATE`, 낙관적 잠금, `SERIALIZABLE`을 더한다. 처음부터 다 하지 않는다.

- 지표: 성공 건수, 처리량, p50·p99, 재시도·직렬화 실패·교착 수
- 다른 시간대 예약이 섞인 부하에서도 따로 잰다
- 예약 오픈 순간의 몰림(NFR-02)을 k6로 재현한다

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 애플리케이션 검사만 | 동시 요청에서 깨진다 (v1에서 확인) |
| advisory lock만 (v1 방식) | 잠금을 빠뜨린 코드 경로가 생기면 DB가 막아 주지 못한다 |
| 유니크 제약 `(방, 날짜, 시작 시각)` | 예약 길이가 달라서 09:00~11:00과 10:00~12:00처럼 시작이 다르면서 겹치는 경우를 못 막는다 (v1에서 확인) |
| Redis 분산 잠금 | DB 안에서 풀 수 있는 문제에 저장소를 하나 더 늘린다. 잠금이 커밋보다 먼저 풀리는 문제도 생긴다 |
