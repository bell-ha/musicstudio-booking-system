# 0013. 카카오·구글 로그인은 인가 코드 + OIDC id_token 한 경로로 처리한다

| 상태 | 날짜 |
|---|---|
| 채택 (구글 구현, 카카오는 나중) | 2026-10-06 |

두 세션이 따로 설계한 뒤 서로 반박해서 합친 결과다.

## 맥락
학생 가입 마찰을 줄이려고 카카오와 구글 로그인을 검토한다. 이 서비스는 무상태 JWT와 SPA를 쓴다. 로컬 이메일 가입은 이메일 소유를 검증하지 않는다.

## 결정
- **흐름 (두 제공자 같음):** 프론트가 제공자 인가 페이지로 보낸다(scope `openid`, `state`·`nonce`는 브라우저에서 만든다). 돌아온 `code`를 `POST /api/v1/auth/social/{google|kakao}`로 보낸다. 백엔드는 허용된 `redirectUri`인지 확인하고, 클라이언트 시크릿으로 토큰을 교환하고, `id_token`의 서명(JWKS)·`iss`·`aud`·`exp`·`nonce`를 검증한다. 그다음 기존과 같은 접근 토큰을 준다.
- 검증은 이미 있는 `NimbusJwtDecoder.withJwkSetUri`에 검증기를 붙여서 한다. 새 라이브러리는 없다. 제공자 토큰은 저장하지 않는다.
- **스키마:** `user_account.password_hash`와 `email`을 NULL 허용으로 바꾸고, `google_subject`와 `kakao_subject` 컬럼(UNIQUE)을 더한다.
- **계정 연결 정책:**
  1. subject로 찾으면 로그인한다.
  2. 같은 이메일의 계정이 이미 있으면 **자동 연결하지 않고** 409 `SOCIAL_EMAIL_IN_USE`를 준다.
  3. 둘 다 아니면 새 계정을 만든다. 이메일은 제공자가 검증했다고 보증한 경우(구글 `email_verified=true`)에만 저장한다. 카카오 이메일은 검증 클레임이 없으면 저장하지 않는다.
- **테스트:** `SocialVerifier` 경계를 두고 연결 정책은 가짜 구현으로 테스트한다. 토큰 교환과 검증은 테스트용 RSA 키와 `MockRestServiceServer`로 확인한다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 같은 이메일이면 자동 연결 (artist-promotion-platform 방식) | 검증되지 않은 이메일로 남의 계정을 가져갈 수 있다 |
| 제공자가 검증한 이메일이면 자동 연결 | 우리 로컬 이메일은 검증된 적이 없다. 공격자가 피해자 이메일로 먼저 로컬 가입해 두면, 진짜 주인이 소셜 로그인할 때 공격자 계정에 연결된다(사전 계정 탈취) |
| 위와 같이 연결하되 연결할 때 로컬 비밀번호 삭제 | 공격자가 이미 받은 접근 토큰(12시간, 폐기 수단 없음)이 계속 통하고, 공격자가 만든 기관과 예약이 피해자 계정에 섞인다 |
| 구글은 id_token을 직접, 카카오만 코드 교환 | 경로가 둘이 된다. 카카오 JS SDK v2는 어차피 코드 방식이다 |
| `social_identity` 테이블 | 제공자 2개, 계정당 제공자별 1개라 컬럼 2개면 된다. 제공자가 3개 이상이 되면 테이블로 바꾼다 |
| Spring Security `oauth2Login` | 세션과 서버 리다이렉트 기반이라 무상태 JWT + SPA에 맞지 않는다 |
| 검증되지 않은 이메일도 저장 | 그 이메일의 진짜 주인이 나중에 가입할 수 없게 된다 |

## 결과
- 엔드포인트 1개, 마이그레이션 1개, 프론트 콜백 화면 1개, 제공자 앱 등록 2곳.
- 공격자가 이메일을 선점했다면 진짜 주인은 그 이메일로 가입할 수 없다. 계정 탈취보다 나은 실패다. 비밀번호 재설정이나 로컬 이메일 검증이 생기면 자동 연결을 다시 검토한다.
- 개발은 `http://localhost` 리다이렉트로 할 수 있다. 운영 공개에는 HTTPS 도메인과 구글 동의 화면 공개(개인정보처리방침 URL)가 필요하다.
