# 0014. 원생 연락처는 애플리케이션에서 AES-256-GCM으로 암호화해 저장한다

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-10-06 |

## 맥락
원생과 보호자의 전화번호를 저장한다. 원생 상당수가 미성년자다(NFR-04). 원장·실장은 실제로 전화를 걸어야 하므로 원문을 볼 수 있어야 하고, 강사와 목록 화면에서는 가려야 한다. 연락처로 검색하는 기능은 MVP에 없다.

## 결정
- JPA `AttributeConverter` 하나(`EncryptedStringConverter`)로 `phone_enc`, `guardian_phone_enc` 컬럼을 AES-256-GCM으로 암호화한다. 행마다 무작위 IV(12바이트)를 암호문 앞에 붙인다.
- 키는 환경 변수 `APP_CRYPTO_KEY`(base64 32바이트)다. 없거나 길이가 틀리면 서버가 뜨지 않는다(JWT 서명 키와 같은 정책).
- 입력은 숫자만 남겨 10~11자리만 받는다.
- 응답: 관리자의 원생 상세에서만 원문, 목록과 강사 화면은 `010-****-5678`, 학생 본인은 자기 것 원문.
- 엔티티 `toString`에 연락처를 넣지 않는다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| PostgreSQL `pgcrypto`로 DB에서 암호화 | 키가 SQL에 실려 DB 로그나 쿼리 기록에 남을 수 있다 |
| 디스크 암호화만 (RDS 저장 암호화) | DB 접속 권한이 있는 사람이나 백업 덤프에서는 평문이다. 함께 쓰는 것은 좋지만 그것만으로는 부족하다 |
| 검색용 블라인드 인덱스(HMAC) | 연락처 검색 기능이 MVP에 없다 |

## 결과와 운영 전에 정할 것
- DB나 백업이 유출돼도 키가 없으면 연락처를 읽을 수 없다.
- **키 교체:** 지금은 키가 하나라서 바꾸면 기존 행을 읽지 못하고 원생 목록 전체가 실패한다. 운영 전에 키 버전을 암호문 앞에 붙이고 새 키로 다시 암호화하는 절차를 정한다. 키 보관은 SSM Parameter Store(SecureString)로 한다(ADR 0008).
- **AAD(추가 인증 데이터) 없음:** 같은 키로 만든 다른 행·다른 컬럼의 암호문을 옮겨 붙여도 복호화된다. DB 쓰기 권한이 있는 공격자를 전제로 한 위험이라 MVP에서는 받아들이고, 키 버전을 넣을 때 컬럼 이름을 AAD로 함께 넣는다.
- 교차 리뷰에서 나온 지적(다른 세션)을 반영해 남긴 메모다.
