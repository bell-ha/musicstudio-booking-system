# 0016. 수납 금액 한도는 잠금이 아니라 조건부 UPDATE와 CHECK로 지킨다

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-10-06 |

## 맥락
청구서 하나에 입금이 여러 번 들어온다(부분 납부). 받은 금액은 청구액을 넘으면 안 되고, 환불은 받은 금액을 넘으면 안 된다. 같은 청구서에 두 관리자가 동시에 입금하거나, 버튼을 두 번 누를 수 있다.

## 결정
- `invoice.paid_amount`(취소 안 된 입금 − 환불의 합)를 두고 `CHECK (0 ≤ paid_amount ≤ amount)`를 건다.
- 입금은 `UPDATE invoice SET paid_amount = paid_amount + :x WHERE … AND paid_amount + :x <= amount` 한 문장. 0행이면 422.
- 장부(payment)는 추가만 하고, 취소는 `voided_at` + 반대 방향의 같은 조건부 UPDATE.
- 멱등: 장부 INSERT를 맨 앞에서 `ON CONFLICT (organization_id, request_id) DO NOTHING RETURNING id`. 같은 키의 두 번째 요청은 유니크 인덱스에서 첫 요청의 커밋을 기다렸다가 기존 기록을 받는다. 내용이 다르면 409.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 청구서 행 `SELECT … FOR UPDATE` 후 합계를 다시 세기 | 맞게 동작한다(부모 행이 있어 phantom이 없다). 그러나 잠금을 빠뜨린 경로가 생기면 DB가 막지 못한다 |
| 읽고 비교한 뒤 저장 | 두 요청이 같은 값을 읽고 둘 다 저장한다(초과 납부) |
| UNIQUE 위반(23505)을 잡아 새 트랜잭션에서 다시 읽기 | 예외·rollback-only·새 트랜잭션이 필요하다. ON CONFLICT가 같은 일을 한 문장으로 한다 |

## 결과
- 판단과 쓰기가 한 문장이라 잠금 없이 동시 입금 20건 중 1건만 된다(테스트). 조건을 빼면 테스트 4개가 실패하는 것을 확인했다.
- `paid_amount`는 장부의 캐시라 어긋날 수 있다. "paid_amount = Σ장부"를 무작위 200 동작 불변식 테스트로 지킨다.
- 연습실 예약(ADR 0010)과의 대비: **범위 겹침은 잠금 + EXCLUDE, 합계 한도는 조건부 UPDATE + CHECK.** 겹침은 "아직 없는 행"을 막아야 해서 잠글 대상이 없고, 합계는 부모 행 하나에 모여 있어서 그 행의 조건부 UPDATE로 충분하다.
