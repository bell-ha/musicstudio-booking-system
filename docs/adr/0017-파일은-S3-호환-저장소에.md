# 0017. 사용자 파일은 DB가 아니라 S3 호환 객체 저장소에 둔다

| 상태 | 날짜 |
|---|---|
| 채택 (0015를 대체) | 2026-10-06 |

## 맥락
0015에서는 기관 로고 한 장뿐이라 DB(bytea)에 두기로 했다. 그 뒤 사용자(프로젝트 주인)가 "데이터베이스뿐 아니라 파일 저장소도 따로 있어야 한다"고 정했다. 앞으로 학교 로고 같은 큰 이미지, 공지 첨부, 레슨 기록 사진이 들어올 자리이고, 운영은 AWS(ADR 0008)라 S3가 표준이다. 0015의 "다시 볼 조건"(파일이 기관당 한 장을 넘는다)을 앞당긴 것이다.

## 결정
- 파일은 **S3 API**로만 다룬다(`FileStore` 인터페이스 하나, 구현 `S3FileStore`). DB에는 저장소 키만 둔다(`site_logo.storage_key`).
- 로컬·테스트는 **SeaweedFS**(S3 API 서버, Apache 2.0)를 docker-compose와 Testcontainers로 띄운다. 운영은 AWS S3이고, 엔드포인트와 키를 비우면 EC2 역할(기본 자격 증명)을 쓴다. 코드는 같다.
- 공개 로고 URL은 그대로(`/api/v1/public/logos/{무작위 키}`)이고 백엔드가 저장소에서 읽어 준다. CSP·캐시 정책을 바꾸지 않으려는 것이다. 사진이 많아지면 서명 URL로 바꾼다.
- **DB와 저장소의 일관성:** 파일을 먼저 올리고 DB에 키를 쓴다. 트랜잭션이 **커밋되면 옛 파일을 지우고, 롤백되면 방금 올린 파일을 지운다**(TransactionSynchronization). 지우기가 실패해도 응답은 깨지지 않고 남는 파일만 생긴다(로그로 찾는다). 반대로 "DB에 키는 있는데 파일이 없는" 경우는 생기지 않는다.
- 0015 시절 DB에 들어간 로고는 그대로 읽힌다(`bytes`와 `storage_key` 중 하나만, CHECK). 다시 올리면 저장소로 간다.

- **운영 설정:** `APP_STORAGE_ENDPOINT`·키를 비우면 EC2 역할로 S3에 붙는다. `APP_STORAGE_CREATE_BUCKET=false`로 둔다(버킷은 Terraform이 만들고, 기동 때 버킷 확인은 `s3:ListBucket` 권한이 필요하다). 역할에는 그 버킷의 `GetObject`·`PutObject`·`DeleteObject`만 준다.
- 교체·삭제는 로고 행을 잠그고 읽는다(동시 교체에서 고아 파일, 삭제와 교체가 겹쳐 낡은 행 저장이 나지 않게). 롤백 정리는 파일을 올리기 **전에** 등록한다. 공개 로고 읽기는 트랜잭션 밖이라 저장소를 읽는 동안 DB 커넥션을 쥐지 않는다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| DB bytea 유지 (0015) | 사용자 결정. 큰 파일·여러 파일이 들어오면 DB 백업과 복제가 무거워진다 |
| MinIO | 처음 고른 것. 2025년부터 커뮤니티판 이미지를 Docker Hub에서 받을 수 없어(실제로 pull 실패) 로컬·CI 재현성이 깨진다 |
| 서버 디스크(Docker 볼륨) | 블루그린에서 두 컨테이너가 같은 디스크를 봐야 하고, EC2를 다시 만들면 사라진다 |
| 브라우저가 S3에 직접 올리기(서명 URL) | 지금은 파일이 작고 형식 검사(매직 바이트)를 서버에서 해야 한다. 큰 파일이 생기면 그때 |

## 결과
- 로컬, CI, 운영이 같은 S3 API로 동작한다. 저장소를 바꿔도(SeaweedFS ↔ S3) 설정만 바뀐다.
- 테스트가 실제 S3 서버를 띄운다(로고를 올리면 저장소에 생기고, 바꾸면 옛 파일이 지워지는지).
- 저장소가 하나 늘어서 로컬 컨테이너가 4개가 되고, 백업 대상이 DB와 버킷 둘이 된다.
