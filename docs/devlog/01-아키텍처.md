    be -->|"S3 PutObject/GetObject<br/>(로고 파일)"| s3

| 구성 요소 | 하는 일 | 데이터가 사는 곳 |
|---|---|---|
| frontend | React SPA를 Nginx가 내려 주고, `/api/`만 백엔드로 넘김 | 없음 |
| backend | 인증(JWT), 기관·멤버, 연습실, 학원 관리, 수납, 사이트 | 없음 (상태 없는 서버) |

| storage | 로고 같은 파일. 코드는 S3 API만 알아서 AWS S3로 그대로 바꿀 수 있음 (ADR 0017) | 볼륨 `storage-data` |

## 3. 백엔드 모듈과 의존 방향 (ADR 0006, ArchUnit으로 검사)

하나의 Spring 앱 안에서 패키지를 기능 모듈로 나눈 **모듈러 모놀리스**다. 기관마다 모듈(연습실·학원 관리·청구)을 켜고 끈다.

```mermaid
flowchart BT
    common["common<br/>보안·오류·암호화·파일 저장소"]
    account["account<br/>가입·로그인·구글"]
    organization["organization<br/>기관·멤버·초대·모듈 스위치"]
    site["site<br/>기관 사이트·공지·로고"]
    practice["practice<br/>평면도·방·예약 정책·예약"]
    academy["academy<br/>원생·수강·레슨 일정·출결"]
    billing["billing<br/>청구서·입금·환불·영수증"]

    account --> common
    organization --> account
    organization --> common
    site --> organization
    practice --> organization
    academy --> organization
    billing --> academy
    billing --> organization
```

`ModuleDependencyTest`가 막는 것: 연습실 ↔ 학원 관리 서로 의존 금지, 기관은 기능 모듈을 모름, 다른 모듈은 수납을 모름(수납이 수강 이벤트를 받는 쪽), 공통은 어떤 모듈도 모름, `domain`은 `api`·`application`을 모름.

모듈 안 계층:

```mermaid
flowchart LR
    api["api<br/>Controller · 요청/응답 record"] --> app["application<br/>Service · @Transactional · 잠금"]
    app --> domain["domain<br/>엔티티 · 규칙 · Repository"]
    app -.->|"집계·조건부 UPDATE"| jdbc["JdbcClient"]
```

## 4. 요청이 지나가는 길

```mermaid
sequenceDiagram
    autonumber
    participant B as 브라우저
    participant N as Nginx
    participant S as Spring Security
    participant I as OrgAccessInterceptor
    participant C as Controller
    participant V as Service (@Transactional)
    participant P as PostgreSQL

    B->>N: GET /api/v1/organizations/202/billing/invoices
    N->>S: 프록시
    S->>S: Bearer JWT 검증 (없거나 만료 → 401)
    S->>I: 인증된 사용자
    I->>P: 이 기관의 ACTIVE 멤버인가? (아니면 403 not-a-member)
    I->>I: 경로 패턴 → 모듈 (billing → BILLING) 켜져 있나? (403 module-disabled)
    I->>C: @OrgRole 역할 검사 통과 (아니면 403 forbidden)
    C->>V: 요청 record (Bean Validation, 실패 → 400)
    V->>P: 기관 id를 항상 조건에 넣어 조회 (남의 기관 리소스 → 404)
    V-->>C: 결과
    C-->>B: JSON (시각은 기관 시간대 오프셋)
```

멀티테넌시는 **공유 스키마 + 모든 행에 organization_id**(ADR 0005). 검사 순서 1~5는 [API 명세](../architecture/02-API.md) 맨 앞의 표와 같다.

## 5. 핵심 흐름

### 5.1 연습실 예약: 겹침을 막는 두 겹 (ADR 0010, 실험 0001)

```mermaid
sequenceDiagram
    autonumber
    participant St as 학생
    participant Bk as BookingService
    participant P as PostgreSQL

    St->>Bk: POST /practice/bookings {roomId, 14:00~15:30}
    Bk->>Bk: 정책 검사 R3~R6 (운영 시간, 30분 단위, 1회·하루 한도, 예약 열림)
    Bk->>P: pg_advisory_xact_lock('pr:room:방:날짜')
    Bk->>P: pg_advisory_xact_lock('pr:member:멤버:날짜')
    Bk->>P: 겹치는 예약이 있나? (R1 방, R2 사람)
    alt 겹침
        Bk-->>St: 409 booking-conflict
    else 없음
        Bk->>P: INSERT practice_booking
        Note over P: EXCLUDE USING gist (room_id, during &&)<br/>앱 검사를 뚫어도 DB가 마지막으로 막음
        Bk-->>St: 201
    end
```

실험 0001(같은 방 동시 요청): 아무 조치 없음·`FOR UPDATE`는 **커넥션 풀 수(20)만큼 겹친 행이 저장**됐다(없는 행은 잠글 수 없음 = phantom). advisory lock과 EXCLUDE는 매번 1건.

### 5.2 수강 등록 → 레슨 회차 → 청구서 자동 생성

```mermaid
sequenceDiagram
    autonumber
    participant M as 관리자
    participant E as EnrollmentService (academy)
    participant L as LessonScheduleService
    participant A as AutoInvoiceListener (billing)
    participant P as PostgreSQL

    M->>E: POST /academy/enrollments
    E->>P: INSERT enrollment (등록 시점 가격 복사)
    E-)A: EnrollmentRegistered (같은 트랜잭션, 동기)
    A->>A: BILLING 켜짐 && 가격 > 0 ?
    A->>P: INSERT invoice (auto, 기한 = max(시작일, 오늘))
    M->>L: PUT /enrollments/{id}/schedule {요일·시각 1~3개, version}
    L->>P: 잠금: 수강 → 다시 읽기 → 강사·원생 (id 오름차순)
    L->>P: 미래 회차 만들기 (횟수권은 총 회차만큼)
    Note over P: EXCLUDE gist (teacher, during) / (student, during)<br/>강사·원생의 레슨이 겹치지 않음
```

academy는 billing을 모른다. 이벤트를 billing이 받는다(그래서 ArchUnit 규칙이 지켜진다). 알림·정산이 붙으면 Outbox로 바꿀 자리.

### 5.3 입금 기록: 두 번 눌러도 한 번, 초과 입금 불가 (ADR 0016)

```mermaid
sequenceDiagram
    autonumber
    participant M as 관리자 화면
    participant Bs as BillingService
    participant P as PostgreSQL

    M->>Bs: POST /invoices/{id}/payments {requestId(UUID), 금액}
    Bs->>P: INSERT payment ... ON CONFLICT (request_id) DO NOTHING RETURNING id
    alt 같은 requestId가 이미 있음
        Bs->>P: 기존 행 읽기 (내용이 다르면 409 IDEMPOTENCY_KEY_REUSED)
        Bs-->>M: 처음 결과 그대로
    else 새 기록
        Bs->>P: UPDATE invoice SET paid_amount = paid_amount + x<br/>WHERE id = ? AND paid_amount + x <= amount
        alt 0행 갱신 (초과 또는 무효)
            Bs-->>M: 422 (트랜잭션 롤백)
        else 1행
            Bs-->>M: 201
        end
    end
    Note over P: CHECK (0 <= paid_amount <= amount)
```

판단과 쓰기가 한 문장이라 행 잠금 없이도 동시 입금이 합계를 넘지 못한다.

### 5.4 로고 올리기: DB와 파일 저장소를 같이 맞추기 (ADR 0017)

```mermaid
sequenceDiagram
    autonumber
    participant M as 관리자
    participant Sv as SiteService
    participant P as PostgreSQL
    participant S3 as 파일 저장소 (S3 API)

    M->>Sv: PUT /site/logo (PNG·JPEG·WebP, 200KB 이하)
    Sv->>P: 로고 행 잠금 (SELECT … FOR UPDATE)
    Sv->>Sv: afterCompletion 등록: 커밋이면 옛 파일 삭제, 롤백이면 새 파일 삭제
    Sv->>S3: PutObject (새 키)
    Sv->>P: storage_key = 새 키
    P-->>Sv: COMMIT
    Sv->>S3: DeleteObject (옛 키)
```

트랜잭션이 실패해도 저장소에 고아 파일이 남지 않고, 성공하면 옛 파일이 정리된다. 공개 로고 읽기는 트랜잭션 밖에서 한다(느린 저장소가 DB 커넥션을 붙잡지 않게).

### 5.5 구글 로그인 (ADR 0013)

```mermaid
sequenceDiagram
    autonumber
    participant B as 브라우저
    participant G as Google
    participant A as SocialLoginService
    participant P as PostgreSQL

    B->>B: nonce 만들어 저장
    B->>G: 인가 요청 (client_id, redirect_uri, nonce)
    G-->>B: /auth/callback/google?code=…
    B->>A: POST /auth/social/google {code, redirectUri, nonce}
    A->>G: 코드 교환 + ID 토큰 서명·aud·nonce 검증 (트랜잭션 밖, 타임아웃 5초)
    A->>P: google_subject로 계정 찾기 / 없으면 새 계정
    Note over A,P: 같은 이메일의 기존 계정과 자동 연결하지 않음<br/>(사전 계정 탈취 방지). 연결은 로그인한 뒤 "구글 계정 연결"로만
    A-->>B: 우리 서비스 JWT
```
