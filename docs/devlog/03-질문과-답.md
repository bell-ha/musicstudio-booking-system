# 질문과 답

만들면서 물어본 것과 그때의 답을 요약했다. 날짜는 대략의 시기다.

## 진로와 포트폴리오 방향 (2026-10 초)

**Q. 백엔드와 인프라 중 무엇을 더 쳐주나? SQL이 약한데.**
인프라가 SQL을 대신해 주지는 않는다. 신입 백엔드 공고는 거의 모두 Java/Spring + JPA + RDB를 필수로 보고, 인프라는 우대 사항이다. 그래서 방향을 바꾸기보다 이 프로젝트에서 SQL을 직접 쓰며(조건부 UPDATE, EXCLUDE 제약, advisory lock) 채우기로 했다.

**Q. 인프라에 강한 백엔드(7:3)와 백엔드에 강한 인프라(3:7) 중 무엇을?**
**백엔드 7 : 인프라 3.** 신입 문이 가장 넓고, 백엔드에서 SRE·플랫폼으로 옮기기는 쉽지만 반대는 어렵다. 인프라 3만으로도 Terraform, 블루그린 측정, 장애 훈련까지 하면 차별화가 된다. 깊이는 DB보다 좋아하는 네트워크 쪽에서 낸다.

**Q. 금융 쪽으로 가려면?**
금융 IT는 DB 비중이 가장 크다(원장·거래). 핀테크·PG(토스, 카카오페이 등)는 포트폴리오 깊이를 보고, 은행·공기업은 자격증과 전공 필기 비중이 크다. 지금 계획의 "데이터 정합성 + 결제"가 결이 같다. 결론: DB 관리도 필요하니 **백엔드로 간다**(사용자 결정).

**Q. 인프라로 가면 보안도 연관되겠네?**
그렇다. VPC·보안 그룹은 망 분리와 최소 권한, TLS는 암호화, 로그는 침입 탐지의 재료다. 네트워크를 좋아하면 네트워크 보안이 가장 자연스러운 연결고리.

## 배포와 인프라

**Q. 블루그린 배포, AWS, 쿠버네티스, 도커는 어떻게 이해해야 하나?**
층이 다르다. ① 앱(Spring jar) ② 포장(Docker 이미지) ③ 실행 장소(내 노트북 또는 AWS EC2) ④ 관리(서버 1대면 Docker Compose, 여러 대면 Kubernetes). Docker·Kubernetes는 AWS 기능이 아니고, AWS는 그걸 돌릴 컴퓨터를 빌려주는 곳이다.

**Q. Cloudtype이나 NeonDB 같은 플랫폼을 쓰면 너무 쉬운 것 아닌가?**
문제는 쉬워서가 아니라 **면접에서 이야기할 거리가 사라지는 것**. "DB가 외부에 노출됐나", "배포 중에 요청이 끊기나", "되돌리는 데 몇 초", "월 얼마"에 답할 재료를 플랫폼이 가져간다. 공유 자원이라 성능 측정 숫자도 믿기 어렵다.

**Q. 그래서 사람들이 내 컴퓨터에 까는 건가?**
두 경우가 섞여 있다. 로컬에서만 돌리는 것(비용 0, 운영 경험은 없음)과 집 컴퓨터를 서버로 쓰는 것(운영 경험은 생기지만 꺼지면 끝, 보안 위험). 이 프로젝트는 로컬 Docker로 개발하고 AWS에 직접 배포하는 쪽(ADR 0008).

**Q. DB는 어디에 구축하나? v1은 Cloudtype + NeonDB였는데.**
지금은 운영 DB가 없다. 개발은 내 컴퓨터의 Docker PostgreSQL 17, 테스트는 Testcontainers가 띄우는 일회용 PostgreSQL. AWS로 갈 때는 RDS를 프라이빗 서브넷에 두고 EC2 보안 그룹에서만 5432를 연다.

**Q. 도커는 3개가 떠야 하는 것 아닌가?**
개발 중에는 DB(와 파일 저장소)만 Docker로 띄우고, 백엔드·프론트는 고치면 바로 반영되게 밖에서 돌린다. 화면을 한 번에 보려면 `docker compose --profile full up -d --build`로 4개(postgres, storage, backend, frontend)를 다 띄운다. 운영에서는 DB가 RDS라 EC2에는 Nginx + 백엔드만.

**Q. 데이터베이스와 사진 같은 파일은 실제로 어디에 저장되나?**
둘 다 지금은 내 Mac의 Docker 볼륨 안이다. 업무 데이터는 `postgres-data` 볼륨의 PostgreSQL, 로고 같은 파일은 `storage-data` 볼륨의 SeaweedFS(S3 호환)에 저장되고 DB에는 파일의 키(`site_logo.storage_key`)만 둔다. `docker compose down -v`를 하면 지워진다. 배포하면 RDS와 S3로 설정만 바꾼다.

## 외부 서비스

**Q. 외부 서비스 없이 할 수 있는 것은? PG는 허가가 필요한데.**
실제로 막히는 것은 실제 돈이 오가는 결제와 알림톡·문자 실제 발송뿐. 결제는 토스페이먼츠 테스트 키를 계약 없이 받을 수 있지만, 장애 상황(웹훅 중복·순서 바뀜)을 마음대로 만들려면 직접 만든 가짜 PG가 낫다. 이번 범위에서는 PG 없이 **수납 장부**(입금·환불 기록)만 만들었다(ADR 0016).

**Q. 구글 로그인용 GCP 프로젝트에 카드 등록이 필요한가? 예전 프로젝트를 써도 되나?**
OAuth 동의 화면과 클라이언트 ID 발급은 결제 계정 없이 무료다. 카드는 Cloud Run, Storage 같은 유료 서비스를 쓸 때만. 예전 프로젝트를 쓰면 동의 화면에 예전 앱 이름이 떠서, 마디 전용 프로젝트를 본인 계정으로 새로 만들었다. 비밀값은 `.env`(git 제외)에만 둔다.

## 화면과 기능

**Q. v1 평면도는 몇 × 몇 칸이었나?**
v1은 30×30칸 고정(칸 20px, 편집 화면 600×600px)이었고, 실제로 칠한 범위는 네 층 모두 26×26 안이었다. 원장님은 컴퓨터로 편집할 테니 v2는 새 층 기본 60×40, 최대 100×100으로 늘렸다.

**Q. 옮긴 v1 평면도가 왜 안 보이나?**
다른 데모 계정이 만든 기관에 들어 있었다. 지금 쓰는 계정을 그 기관 소유자로 추가해 해결([트러블슈팅 22](02-트러블슈팅.md)).

**Q. VS Code에서 backend 폴더가 왜 빨간색인가?**
코드 오류가 아니라 Java 확장이 낡은 의존성 목록을 쓰는 것. `Java: Reload Projects`([트러블슈팅 21](02-트러블슈팅.md)).

**Q. 기능이 너무 많은데 처음 쓰는 사람은 어떻게 하나? 다른 서비스는 온보딩을 어떻게 하나?**
조사 결과 자동으로 뜨는 투어는 완료율 23%(Chameleon), 튜토리얼을 넘긴 사람과 본 사람의 성공률 차이가 없었다(NN/g). 그래서 투어 대신 **관리자 홈의 "시작하기" 목록**(실제 데이터로 완료 판단)과 **빈 화면 안내**를 만들었다. 두 설계(A·B)를 반박해 합쳤다 → UC-15, FR-ORG-08.
