# 0001. 예약 겹침 방지 방식 비교

| 실행일 | 관련 문서 |
|---|---|
| 2026-10-06 | [ADR 0010](../adr/0010-예약-겹침-방지.md) |

> 이 문서는 `cd backend && ./gradlew experiment`가 만든다. 숫자는 손대지 않는다.

## 목적
같은 방, 같은 시간에 요청이 몰릴 때 겹친 예약이 저장되는지 본다. ADR 0010의 후보 4가지를 같은 조건에서 재고, 막는지와 비용을 비교한다.

## 환경
- CPU: Apple M1 Max, 논리 코어 10개 (JVM 기준)
- OS: Mac OS X 13.7.8 (aarch64)
- Java: OpenJDK 64-Bit Server VM 25.0.1
- PostgreSQL: 17.11 (Debian 17.11-1.pgdg13+2) (Testcontainers postgres:17, 기본 설정)
- Docker: 27.5.1, 엔진에 할당된 CPU 10개, 메모리 7GiB
- 커넥션 풀: HikariCP, 최대 20개 (최소 유휴도 같은 값), 커넥션 대기 한도 1800초
- deadlock_timeout: 1s (기본값)
- 부하 발생기(JVM)와 DB(Docker 컨테이너)가 한 대의 노트북에서 같이 돈다. 네트워크 지연이 거의 없고, CPU를 서로 나눠 쓴다.
- 데이터 양: 실험 테이블은 매 회차 비우고 시작한다. 회차가 끝날 때 많아야 1,000행이다.

## 방법
- 요청 1,000건을 가상 스레드에 하나씩 올린다. 모두 준비되면 `CountDownLatch` 하나로 한꺼번에 놓는다.
- 요청 하나 = 트랜잭션 하나. 격리 수준은 기본값 READ COMMITTED. 앱 서비스를 거치지 않고 JDBC로 직접 보낸다.
- 모든 요청의 시간은 같다: 2026-10-07T10:00:00Z ~ 2026-10-07T11:00:00Z (`[시작, 끝)`).
- 방식 0~2는 배타 제약이 **없는** 테이블(`exp_booking_plain`)에 쓴다. 제약이 있으면 DB가 버그를 가린다. 방식 3만 배타 제약이 있는 테이블(`exp_booking_excl`)에 쓴다.
- 시나리오 A: 1,000건 모두 같은 방. 정답은 저장 1행.
- 시나리오 B: 방 50개에 20건씩. 정답은 저장 50행, 겹친 방 0개.
- 방식마다 3회씩 돌린다. 회차마다 테이블을 비운다. 측정 전에 방식마다 시나리오 B로 워밍업 1회를 돌리고 버린다.

| # | 방식 | 트랜잭션 안에서 하는 일 |
|---|---|---|
| 0 | 아무 조치 없음 | 겹치는 행 `count(*)` → 0이면 INSERT |
| 1 | 겹치는 기존 행에 FOR UPDATE | 겹치는 행 `SELECT ... FOR UPDATE` → 없으면 INSERT |
| 2 | advisory lock (방·날짜) | `pg_advisory_xact_lock(hashtextextended('room:'||방||':'||날짜, 0))` → 검사 → INSERT |
| 3 | EXCLUDE 제약만 | 바로 INSERT. SQLState `23P01`이면 거절로 센다 |

지표 뜻:
- **저장된 행**: 끝난 뒤 테이블에 실제로 남은 행 수. 정확성의 기준이다.
- **겹친 방**: 2행 이상 저장된 방의 수. 0이어야 한다.
- **거절**: 검사에서 겹침을 보고 INSERT를 안 했거나, `23P01`을 받은 수.
- **기타 오류**: 그 밖의 SQL 예외. SQLState로 나눈다 (`40P01` 교착, `40001` 직렬화 실패).
- **p50·p99**: 요청 하나의 시간. 커넥션 풀 대기를 포함한다. 처리량 = 1,000 / 전체 시간.

## 해석
<!-- 수동 해석 시작 -->
1. **겹침 검사를 앱에서만 하면 막지 못한다.** 방식 0은 같은 방에 1,000건이 몰리자 매번 20행이 저장됐다. 20은 커넥션 풀 크기다. [추측] 커넥션을 잡은 20개 트랜잭션이 아무도 커밋하기 전에 "겹치는 행 없음"을 함께 본 것이다.
2. **겹치는 행에 `FOR UPDATE`를 걸어도 같다.** 방식 1도 매번 20행이다. 아직 겹치는 행이 없어서 잠글 대상이 없다(phantom). 느려지기만 했다(처리량 약 1/4). 흔한 "재고 감소" 동시성 예제의 방법이 범위 규칙에서는 통하지 않는다는 근거다.
3. **배타 제약(EXCLUDE)만 두면 정확하지만 한 칸에 몰리면 무너진다.** 방식 3은 항상 1행이지만, 1,000건 중 569~594건이 교착(`40P01`)으로 끝났고 한 회차에 약 8분, p99 약 480초가 걸렸다. PostgreSQL 소스(`execIndexing.c`)의 주석대로, 배타 제약은 인덱스 항목을 먼저 넣고 나서 충돌을 검사한다. 그래서 동시에 넣은 트랜잭션들이 서로의 미확정 행을 기다리다 교착이 나고, 교착 감지(`deadlock_timeout` 1초)마다 멈춤이 이어진다. 사용자로서는 정답이 1건인데 나머지 절반 넘게가 "충돌" 대신 오류와 몇 분의 대기를 받는다.
4. **방·날짜 advisory lock은 정확하고 안정적이다.** 방식 2는 항상 1행, 오류 0, p99 약 0.8초다. 같은 방 요청을 줄 세우므로 배타 제약의 교착이 생기지 않는다.
5. **요청이 여러 방에 흩어지면(시나리오 B) 배타 제약만으로도 충분하고, advisory lock은 왕복이 하나 늘어 약 30% 느리다** (약 7,000 대 10,000 req/s). 방식 0은 이 경우에도 겹친 방이 생겼다.

**결론 (ADR 0010):** 예약 오픈 순간처럼 한 칸에 몰리는 상황이 이 서비스의 실제 부하(v1의 금요일 09:00)라서, 방·날짜 advisory lock으로 줄 세우고 배타 제약은 잠금을 빠뜨린 경로를 막는 마지막 방어선으로 둔다. 흩어진 부하에서 30% 느린 비용은 받아들인다.

## 한계
- 부하 발생기와 DB가 한 기계에 있다. 절대 수치(처리량, 지연)는 이 기계에서만 뜻이 있다. 방식끼리의 상대 비교로만 본다.
- 네트워크 왕복이 거의 0이다. 실제 배포에서는 트랜잭션이 길어져 경쟁 구간이 넓어진다.
- 회차가 3번뿐이다. 분산을 말하기에는 적다.
- JDBC로 직접 잰다. JPA, 검증 로직, HTTP는 빠져 있다. R2(같은 사람), R4(하루 한도)는 재지 않았다.
- PostgreSQL은 컨테이너 기본 설정이다. 튜닝하지 않았다.
