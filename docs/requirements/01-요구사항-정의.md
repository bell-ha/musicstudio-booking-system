## 1. 배경

### v1에서 배운 것
이 프로젝트의 전신은 단국대학교 뉴뮤직학부 연습실 예약 서비스(v1)다. 2025-03부터 2026-07까지 학부 학생들이 실제로 썼다. 코드는 `legacy-fastapi` 브랜치와 `v1-fastapi` 태그에 보관했다.

운영하면서 확인한 것:

| 배운 것 | v2에 반영 |
|---|---|
| 예약 시스템의 본질은 화면이 아니라 "겹치면 안 되는 규칙"이다. 같은 방, 같은 사람, 같은 날에 걸리는 규칙이 각각 다르다 | 겹침 규칙을 DB 제약까지 내려서 지킨다 (NFR-01) |
| 매주 정해진 시각에 예약을 열면 그 순간 요청이 몰린다. 동시 요청이 실제로 겹쳐 들어갈 수 있었다 | 몰림을 측정 대상으로 삼는다 (NFR-02) |
| 평면도와 예약 정책이 코드에 있으면 바꿀 때마다 재배포해야 했다. 데이터로 옮기자 관리자가 직접 바꿨다 | 기관 설정은 전부 데이터로 둔다 (NFR-05) |
| 비밀번호를 평문으로 저장하던 것을 운영 중에 발견해 점진적으로 전환했다 | 처음부터 해시로 저장한다 (NFR-04) |
| 학교 계정 연동이 없어서 가입 후 관리자 승인 절차를 두었다 | 가입 코드 + 승인 방식으로 일반화한다 (FR-ORG-04) |
| 공용 PC에 로그인이 남는 문제가 있었다 | 기관별 세션 만료 설정 (NFR-06) |

### 새로 넓히는 이유
- 음악학원 원장에게서 "안내, 결제, 수업 일정 관리가 너무 어렵다"는 요청을 받았다.
- v1은 한 학부 전용이었다. 같은 문제를 가진 학원과 학교가 많다.
- 기존 학원관리 서비스는 반 단위 운영에 맞춰져 있다. 학부모가 앱을 설치하고 가입해야 하는 부담이 가장 큰 불만으로 꼽힌다.

## 2. 목표와 범위

### 목표
| # | 목표 |
|---|---|
| G1 | 누구나 가입해서 자기 기관(학원, 학교)을 만들고, 설정을 코드 수정 없이 직접 바꾼다 |
| G2 | 기관마다 필요한 기능 모듈만 켜서 쓴다. 연습실 예약만 써도 되고 전부 써도 된다 |
| G3 | 겹치면 안 되는 예약은 동시 요청이 몰려도 절대 겹치지 않는다 |
| G4 | 원장과 강사가 원생의 수강 상태와 레슨 기록을 한곳에서 관리한다 |
| G5 | 보호자는 계정을 만들지 않는다 |

### 이번 버전의 범위 밖
- 보호자 계정과 보호자 앱
- 네이티브 앱 (반응형 웹으로 만든다)
- 게시판(댓글·답글·글쓰기를 여럿이 하는 것), 채팅. 관리자가 쓰는 한 방향 **공지**는 0.3부터 범위 안이다 (FR-SITE-03)
- 외부인 대관과 중개
- 실제 결제와 실제 문자 발송 (테스트 환경만 쓴다)
- 기관끼리 데이터 공유

## 3. 사용자

| 역할 | 하는 일 | 학원에서 | 학교에서 |
|---|---|---|---|
| 소유자 (OWNER) | 기관을 만든 사람. 모든 권한, 관리자 지정, 모듈 설정 | 원장 | 학과장, 담당 교수 |
| 관리자 (MANAGER) | 소유자가 맡긴 운영. 멤버 승인, 연습실·원생 관리 | 실장 | 조교, 학생회 |
| 강사 (TEACHER) | 담당 학생 확인, 레슨 기록 | 강사 | 교수, 레슨 강사 |
| 학생 (STUDENT) | 연습실 예약, 내 수강 정보 확인 | 원생 | 학생 |
| 보호자 | **계정 없음.** 원생 정보에 이름과 연락처만 저장한다. 알림과 결제는 2차에서 로그인 없는 링크로 받는다 | 학부모 | |

- 한 계정이 여러 기관에 서로 다른 역할로 속할 수 있다. 예: A학원 강사이면서 B학교 학생.
- 역할은 기관 안에서만 의미가 있다.

## 4. 기능 모듈

| 모듈 | 내용 | 비고 |
|---|---|---|
| 기본 | 기관, 멤버, 역할, 가입 | 항상 켜져 있다 |
| 기관 사이트 (0.3) | 로고·소개·연락처, 기관 색, 공지, 공개 소개 페이지 | 항상 켜져 있다 |
| 연습실 | 층과 평면도, 방과 장비, 예약 정책, 예약 | 켜고 끌 수 있다 |
| 학원 관리 | 과목, 수업 상품, 원생, 수강 등록, 레슨 기록 | 켜고 끌 수 있다 |
| 레슨 일정 (2차) | 강사 가능 시간, 고정 일정, 회차, 빈 시간 신청, 출결, 보강 | 학원 관리 모듈이 필요하다 |
| 청구·결제 (2차) | 청구서, 결제, 대사 | 학원 관리 모듈이 필요하다 |
| 알림 (2차) | 휴강·결제 안내, 대체 채널 | |

- 모듈을 끄면 그 모듈의 화면과 API를 쓸 수 없다. 데이터는 지우지 않는다. 다시 켜면 그대로 돌아온다.

## 5. 기능 요구사항

우선순위: **M** = MVP (2026-12) · **2** = 2차 (2027-02) · **L** = 나중

### 5.1 기본

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-ORG-01 | 이메일과 비밀번호로 가입하고 로그인한다 | M |
| FR-ORG-02 | 기관을 만든다. 이름, 유형(학원/학교/기타), 시간대. 만든 사람이 소유자가 된다 | M |
| FR-ORG-03 | 소유자는 기관 이름을 바꾸고 모듈을 켜고 끈다. 모듈을 꺼도 데이터는 지우지 않는다. 시간대는 만들 때 정하고 바꾸지 않는다 | M |
| FR-ORG-04 | 가입 방식은 두 가지다. **초대 링크**(역할 지정, 만료 시각, 1회용) 또는 **가입 코드 + 승인**(신청하면 대기 상태, 관리자가 승인) | M |
| FR-ORG-05 | 관리자는 가입 신청을 승인하거나 거절하고, 멤버의 역할을 바꾸거나 비활성화·재활성화한다. 소유자 지정과 관리자 지정, 소유자·관리자에 대한 변경은 소유자만 한다. 마지막 소유자는 강등하거나 비활성화할 수 없다. 비활성화해도 이미 잡힌 예약은 그대로 두고, 필요하면 관리자가 취소한다 | M |
| FR-ORG-06 | 사용자는 자기가 속한 기관 목록을 보고 기관을 전환한다 | M |
| FR-ORG-07 | 기관 설정으로 세션 만료 방식을 정한다 (기본 / 매일 정해진 시각에 로그아웃) | L |

### 5.2 연습실

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-PR-01 | 관리자는 층을 추가하고 이름과 순서를 정한다 | M |
| FR-PR-02 | 관리자는 층마다 격자 평면도를 편집한다. 벽과 복도를 칠하고 지우고, 방을 배치한다 | M |
| FR-PR-03 | 관리자는 방 정보를 관리한다. 이름, 수용 인원, 장비 목록, 사용 가능 여부(점검 중이면 예약 불가) | M |
| FR-PR-04 | 관리자는 예약 정책을 정한다 (아래 표) | M |
| FR-PR-05 | 학생은 층 평면도에서 날짜와 시각을 고르면 **방마다 비어 있는지 지도 위에 표시된 것**을 본다 | M |
| FR-PR-06 | 학생은 지도에서 방을 눌러 그날 시간표를 보고 예약한다 | M |
| FR-PR-07 | 학생은 내 예약 목록을 보고 취소 마감 전까지 취소한다 | M |
| FR-PR-08 | 관리자는 날짜별 전체 예약 현황(방 × 시간)을 보고, 사유를 적어 예약을 강제 취소한다 | M |
| FR-PR-09 | 지도의 빈 방 표시가 다른 사람의 예약에 따라 새로고침 없이 바뀐다 | L |
| FR-PR-10 | 방을 점검 처리하면 그 기간의 예약을 한 번에 취소하고 사유를 남긴다 | L |
| FR-PR-11 | 층을 통째로 복사한다 | L |
| FR-PR-12 | 관리자가 계정 없는 원생 대신 예약한다 | L |

**예약 정책 항목 (FR-PR-04)**

| 항목 | 예 | v1 |
|---|---|---|
| 운영 시간 (요일별) | 09:00~23:00 | 있음 |
| 시간 단위 | 30분 / 60분 | 있음 |
| 1회 최대 연속 이용 | 2시간 | 있음 |
| 1인 하루 최대 이용 | 3시간 | 없음 |
| 예약 오픈 방식 | 항상 N일 앞까지 / 매주 정해진 요일·시각에 다음 주(월~일)를 연다 | 매주 금 09:00 |
| 취소 마감 | 시작 10분 전 | 있음 |

- 예약 하나는 기관 현지 날짜 하루 안에 있다. 자정을 넘는 운영 시간은 지원하지 않는다.
- 나중: 같은 날 재예약 규칙(v1의 3종), 예약할 수 있는 역할.

### 5.3 학원 관리

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-AC-01 | 관리자는 과목을 관리한다 (피아노, 보컬, 기타, 작곡 등) | M |
| FR-AC-02 | 관리자는 수업 상품을 만든다. 과목, 형태(1:1), 종류(횟수권 N회 / 기간권 N개월), 레슨 길이, 가격 | M |
| FR-AC-03 | 관리자는 원생을 등록한다. 이름, 출생연도, 연락처, 보호자 이름·연락처(미성년), 메모. 원생은 계정이 없어도 된다. 학생 계정이 있으면 연결한다 | M |
| FR-AC-04 | 관리자는 수강을 등록한다. 원생 + 상품 + 담당 강사 + 시작일을 넣으면 종료일 또는 총 회차가 정해진다. 상태: 수강 중 / 일시정지 / 종료 / 환불 | M |
| FR-AC-05 | 관리자는 수강을 연장하거나 강사를 바꾸거나 일시정지한다 | M |
| FR-AC-06 | 관리자는 원생 목록을 과목, 강사, 상태로 거르고, **만료 임박**(종료일이 N일 이내) 원생을 모아 본다. 횟수권의 남은 회차는 출결이 들어오는 2차에서 다룬다 | M |
| FR-AC-07 | 강사는 수강 중인 담당 학생 목록을 본다 | M |
| FR-AC-08 | 강사는 학생별로 레슨 기록을 남긴다. 날짜, 진도, 숙제, 메모, 학생 공개 여부(기록 전체 단위). 소유자와 관리자는 모두 볼 수 있고, 학생은 공개된 기록만 본다 | M |
| FR-AC-09 | 원생 상세 화면에서 수강 이력과 레슨 기록을 시간순으로 본다 | M |
| FR-AC-10 | 그룹 수업 (정원이 있는 수업) | L |
| FR-AC-11 | 엑셀로 원생 일괄 등록 | L |
| FR-AC-12 | 관리자는 수강마다 고정 일정(요일과 시작 시각, 주 1~3회)을 정한다. 레슨 길이는 상품을 따른다. 시스템은 수강이 끝날 때까지 회차를 만든다. 같은 강사나 같은 원생의 회차가 겹치면 거절하고 겹치는 날짜를 알려 준다 (0.3) | M |
| FR-AC-13 | 관리자는 기관 전체, 강사는 자기 회차를 날짜별·주별로 본다. 출결을 안 남긴 지난 회차를 모아 본다 (0.3) | M |
| FR-AC-14 | 담당 강사와 관리자는 회차에 출석·결석·사전 결석과 메모를 남긴다. 출석·결석은 회차가 시작한 뒤에만, 사전 결석은 언제나 남긴다. 횟수권은 출석과 결석만 차감하고, 사전 결석·휴강한 만큼 뒤에 회차를 이어 붙인다 (0.3) | M |
| FR-AC-15 | 관리자는 회차를 휴강하거나(사유 필수) 그날 전체를 휴강하고, 보강 회차를 날짜·시각을 정해 넣는다 (0.3) | M |
| FR-AC-16 | 학생은 자기 회차 일정과 출결, 횟수권의 남은 회차를 본다 (0.3) | M |
| FR-AC-17 | 수강 일시정지·종료·환불은 앞으로의 회차를 지우고, 재개·연장·강사 변경은 앞으로의 회차를 다시 맞춘다. 지난 회차와 출결은 그대로 둔다 (0.3) | M |

### 5.4 기관 사이트 (0.3)
원장이 블로그·카페처럼 기관을 꾸미고 알린다. `site` 모듈, 모든 기관에서 켜져 있다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-SITE-01 | 관리자는 로고(PNG·JPEG·WebP, 200KB 이하), 소개 글, 주소, 대표 번호, 운영 안내를 바꾼다. 기관 홈과 앱 바에 보인다 | M |
| FR-SITE-02 | 관리자는 기관 색을 미리 정한 6색 중에서 고르거나 직접 고른다. 흰 글자 대비 4.5:1 이상만 받고, 화면은 너무 밝은 색을 같은 색조로 진하게 맞춘다. 주 버튼·선택 상태·기관 머리의 색이 바뀌고, 예약 상태 색은 바뀌지 않는다 | M |
| FR-SITE-03 | 관리자는 공지를 쓰고 고치고 지우고 고정한다. 공개 범위는 강사 이상 / 멤버 전체 / 외부 공개. 멤버는 자기 범위의 공지만 본다. 댓글·첨부·조회수는 없다 | M |
| FR-SITE-04 | 소유자는 공개 소개 페이지를 켜고 주소(`/s/주소`)를 정한다. 방문자는 로그인 없이 소개, 연락처, 외부 공개 공지를 본다 | M |
| FR-SITE-05 | 소유자가 "가입 신청 받기"를 켜면 방문자는 공개 페이지에서 가입을 신청한다. 가입 코드는 공개하지 않는다 | S |

### 5.5 2차 (요약)
상세는 2차 시작 전에 이 문서에 추가한다.
- **레슨 일정 (나머지):** 강사 가능 시간, 학생 빈 시간 신청, 보강 정책(월 상한 등), 레슨실 배정. 고정 일정·회차·출결·휴강·보강은 0.3에서 5.3으로 옮겼다
- **청구·결제:** 청구 규칙, 월 청구, 로그인 없는 결제 링크, 결제 결과 통보 처리, 대사
- **알림:** 휴강·결제 안내, 재시도와 대체 채널, 발송 결과

## 6. 비기능 요구사항

| ID | 요구사항 | 검증 방법 |
|---|---|---|
| NFR-01 정합성 | 같은 방, 같은 시간의 유효한 예약은 1건이다. 같은 사람, 같은 시간의 유효한 예약은 방이 달라도 1건이다. 하루 최대 이용 같은 정책 한도도 동시 요청에서 지켜진다 | 동시 요청 테스트, 1,000건 부하 |
| NFR-02 몰림 | 예약 오픈 순간 요청이 몰려도 에러 없이 처리한다. 목표 수치(동시 사용자 수, p99)는 첫 측정 후 정한다 | k6 부하 테스트, 측정 환경 기록 |
| NFR-03 기관 격리 | 다른 기관의 데이터는 조회도 수정도 할 수 없다 | 모든 API에 다른 기관 접근 테스트 |
| NFR-04 보안 | 비밀번호와 초대 링크 토큰은 해시로만 저장한다. 가입 코드는 승인을 거치므로 원문으로 저장한다. 연락처는 암호화해서 저장하고 화면과 로그에서 가린다. 모든 통신은 HTTPS. 공개 페이지는 정해 둔 항목만 내보내고, 업로드는 파일 앞부분(매직 바이트)으로 형식을 확인하며 SVG는 받지 않는다. 소개·공지는 평문으로만 받는다 | 테스트, 점검 도구 |
| NFR-05 설정은 데이터 | 정책, 평면도, 모듈 설정을 바꾸는 데 배포가 필요 없다 | |
| NFR-06 세션 | 기관이 정한 세션 만료 방식을 따른다 | |
| NFR-07 사용성 | 휴대폰 브라우저를 먼저 고려한다. 앱 설치 없이 쓴다 | |
| NFR-08 시간 | 모든 시각은 시간대를 포함해 저장하고, 기관의 시간대로 보여 준다 | |
| NFR-09 감사 | 나중. MVP에서는 강제 취소 사유만 예약에 남긴다 | |

## 9. 0.2에서 줄인 것

설계를 최소로 유지한다는 원칙(필요 없으면 만들지 않는다)에 따라 0.1에서 뺐다.

| 뺀 것 | 이유 |
|---|---|
| 같은 날 재예약 규칙, 예약할 수 있는 역할 | R2(같은 사람 겹침 금지)와 하루 최대만으로 MVP 요구를 채운다 |
| 대신 예약 | 원생 기록과 예약 대상을 둘로 나눠야 해서 모델이 복잡해진다 |
| 층 복사 | 편의 기능 |
| 수강 변경 이력, 감사 기록 | 화면도 유스케이스도 없다 |
| 강사 담당 과목, 수강 등록 경고 | 경고를 위해 테이블과 확인 흐름이 하나씩 더 필요하다 |
| 횟수권 남은 회차 | 회차를 줄이는 출결이 2차다 |
| 기관 생성 수 제한 | 악용이 실제로 생기면 넣는다 |
